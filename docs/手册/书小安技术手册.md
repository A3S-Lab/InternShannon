## 2. 进程模型与桌面外壳

### 2.1 Sidecar 生命周期

Tauri 主进程在启动时 spawn 一个 Node 子进程运行 sidecar。环境变量在 `apps/desktop/src-tauri/src/server.rs:772` 附近注入：

```text
APP_HOST = 127.0.0.1
APP_PORT = 29653
```

Node 运行时与 sidecar 的编译产物都随安装包分发，不依赖用户机器上已安装的 Node。资源清单见 `tauri.conf.json` 的 `bundle.resources`：

```json
"resources": {
  "resources/sidecar/": "",
  "resources/node/": "node/",
  "resources/search-browser/": "search-browser/"
}
```

sidecar 的 stdout / stderr 重定向到临时目录下的
`internshannon_sidecar_{stdout|stderr}_{pid}.log`（`server.rs:106-111`）。

前端在 `BackendStartupGuard` 中轮询 `/api/v1/health`，最长等待 60 秒，期间显示启动遮罩。

### 2.2 网络边界约束

三处约束共同保证 webview 的 HTTP 流量不出本机：

**Tauri 命令白名单** —— `loopback_http_request` 在 `apps/desktop/src-tauri/src/lib.rs:936-951` 校验协议必须为 `http`，主机必须为回环地址，否则拒绝。

**CSP** —— `tauri.conf.json:26` 的 `connect-src` 显式列出 `http://127.0.0.1:29653` 与 `ws://127.0.0.1:29653`。

**能力声明** —— `apps/desktop/src-tauri/capabilities/default.json` 逐项授予 fs、dialog、shell、http 能力，其中 http 的 scope 限定为 `http://127.0.0.1:29653`。

需要明确：这三条约束的对象是 webview 发起的请求。sidecar 进程本身访问外部 LLM API 不受此约束，那是产品运行的必要条件。

### 2.3 Tauri 配置文件

外壳的 UI 偏好（文件监听、编辑器自动保存等）存放在 `~/.internshannon/config.hcl`，首次启动若不存在则写入默认值（`apps/desktop/src-tauri/src/config.rs:157-166`）。这份配置与 sidecar 的 `config.json` 是两套独立存储。

## 3. Sidecar 服务层

### 3.1 模块划分

```text
apps/sidecar/src/
├── modules/
│   ├── assets/     知识库与资产
│   ├── config/     设置读写

├── shared/
│   ├── api/            响应封装、拦截器、过滤器、OpenAPI 装饰器
│   ├── security/       路径校验、密钥打码
│   ├── observability/  指标与日志
│   └── infrastructure/ 桌面路径、持久化基类
└── runtime/desktop/    桌面运行时模块装配
```

### 3.2 DDD 分层

业务模块统一采用四层结构：

```text
modules/<name>/
├── domain/          实体、值对象、仓储与服务接口、DI token
├── application/     命令、查询、处理器、应用服务
├── infrastructure/  持久化与外部实现
├── presentation/    控制器、网关、请求与响应 DTO
└── <name>.module.ts
```

强制规则：

1. `domain/` 层为无框架依赖的纯 TypeScript，不得 import NestJS、HTTP、数据库或桌面 API。
2. 业务模块通过接口 token 消费基础设施，不直接依赖具体实现类。
3. DTO 只放在 `presentation/dto/request` 或 `presentation/dto/response`，应用服务不携带 HTTP DTO。
4. 控制器保持瘦身，委托给 `CommandBus`、`QueryBus` 或应用服务。

边界由 `pnpm --filter @internshannon/sidecar run ddd:check`（或 `just ddd`）静态校验。

### 3.3 API 响应约定

所有端点复用共享的拦截器与异常过滤器，响应封装统一。

成功：

```json
{
  "code": 200,
  "message": "Success",
  "data": {},
  "requestId": "uuid",
  "timestamp": "2026-04-17T00:00:00.000Z"
}
```

失败：

```json
{
  "code": 404,
  "statusCode": "NOT_FOUND",
  "message": "Resource not found",
  "details": {},
  "requestId": "uuid",
  "timestamp": "2026-04-17T00:00:00.000Z"
}
```

`code` 为 HTTP 状态码，`statusCode` 为业务错误码或框架错误标识。

### 3.4 时间戳规范

后端时间戳必须无歧义，时区转换只在前端展示层进行。

- 持久化使用带时区的 ISO 8601，或 epoch 毫秒。
- API 响应时间戳必须带 `Z` 或 `+08:00` 后缀。
- 禁止把 `toLocaleString()`、`toLocaleDateString()`、`toString()` 的结果写入数据库、API 响应、审计日志、SSE 负载或 webhook。
- `Date.now()`、`Date.parse()`、`.getTime()` 是 UTC epoch 操作，可安全使用。

| `workspace.controller.ts` | 22 | 文件读写、二进制读写、重命名、复制、删除、搜索、替换、git 状态 |

## 4. 智能体运行时

### 4.1 会话创建

`kernel-session-runtime-factory.service.ts` 负责组装运行时配置并创建会话：

```text
读取设置（provider、model、apiKey）
  → 解析工作区 cwd
  → 组装 skillDirs 与 mcpServers
  → 计算 permissionPolicy 与 confirmationPolicy
  → Agent.create(...) → agent.session(...)
```

会话的 `cwd` 绑定到真实目录。默认为 `{workspaceRoot}/users/{userId}/sessions/{agentId}-{timestamp}`，工作区根目录默认 `~/.internshannon/workspace`，可在设置中改为任意目录。

### 4.2 默认模型解析

`kernel-runtime-config.builder.ts` 的 `resolveDefaultModel()` 按 `provider/model` 格式解析默认模型，并校验对应 API key 存在。若未配置且无环境变量兜底，抛出 `No AI model configured`。

已知 provider 预设：

| key | 标签 | 默认 base URL |
|---|---|---|
| `anthropic` | Anthropic | `https://api.anthropic.com` |
| `openai` | OpenAI | `https://api.openai.com/v1` |
| `zhipu` | 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` |
| `openai-compatible` | OpenAI 兼容接口 | 用户填写 |

环境变量兜底：`OPENAI_API_KEY`、`ANTHROPIC_API_KEY`、`ZHIPU_API_KEY`。

### 4.3 消息流与事件

`kernel-message-runner.service.ts` 消费 SDK 的流式事件，转发到前端 WebSocket 通道，并负责：

- 流式增量转发
- 工具调用事件与确认事件的桥接
- 卡流检测与恢复
- 取消传播

### 4.4 工具失败熔断

`kernel-tool-failure-policy.ts` 定义连续失败阈值：

| 范围 | 阈值 |
|---|---|
| 同一工具连续失败 | 3 次 |
| `web_search` 连续失败 | 2 次 |
| 跨工具累计连续失败 | 4 次 |

达到阈值后中断当前工具循环，避免智能体在失败路径上空转。

### 4.5 确定性预检索

`kernel-message-runner.service.ts:2488-2506` 中存在一条确定性预检索路径：当用户消息匹配正则
`/(?:个人|我的|我)知识库|personal\s+knowledge\s+base/i`
时，在调用模型前先执行一次知识库检索并把结果注入上下文。这是一条窄触发路径，不是通用 RAG 前置。

## 5. 权限与确认机制

权限控制分两层：会话级策略（交给 SDK）与服务端确认门（自行实现）。

### 5.1 第一层：会话策略

`apps/sidecar/src/modules/kernel/application/kernel-session-policies.ts`

**权限策略**：

```ts
export function permissionPolicyForMode(permissionMode?: string, hitlEnabled = true) {
    if (permissionMode === 'auto' || permissionMode === 'plan') {
        return { defaultDecision: 'allow' };
    }
    if (!hitlEnabled) return undefined;
    return {
        allow: [...READONLY_PERMISSION_TOOLS],
        defaultDecision: 'ask',
    };
}
```

`READONLY_PERMISSION_TOOLS` 列出 19 个只读工具名（`read`、`ls`、`glob`、`grep`、`search`、`web_search` 及其大小写变体等）。这些工具自动放行，其余工具默认 `ask`。

**确认策略**：

```ts
export function confirmationPolicyForMode(permissionMode?: string, hitlEnabled = true) {
    if (permissionMode === 'auto' || permissionMode === 'plan' || !hitlEnabled) {
        return undefined;
    }
    return {
        enabled: true,
        defaultTimeoutMs: 60_000,
        timeoutAction: 'reject',
        yoloLanes: ['query'],
    };
}
```

超时 60 秒，超时动作为拒绝。

**三种执行模式对权限的影响**：

| 模式 | permissionPolicy | confirmationPolicy | 说明 |
|---|---|---|---|
| `default` 默认模式 | 只读放行，其余 ask | 启用 | 正常执行 |
| `plan` 规划模式 | `allow` | 未启用 | 但由 `planReadonlyToolBlockReason` 在 hook 层拦截非只读工具 |
| `auto` 自动执行 | `allow` | 未启用 | 不逐次确认 |

`plan` 模式的只读限制不靠 permissionPolicy 实现，而是靠 `isReadOnlyToolName()` 在 hook 事件中判定并返回阻断原因（`kernel-session-policies.ts:80-96`）。该函数按名称子串匹配（含 `read` / `list` / `ls` / `grep` / `glob` / `find` / `inspect` / `status` / `get` / `fetch` / `open` / `search` 判为只读）。

### 5.2 第二层：服务端确认门

`kernel-tool-confirmation.service.ts` 拦截 SDK 发出的 `confirmation_required` 事件，把确认请求推给前端，并且必须调用 `session.confirmToolUse(toolId, approved, reason)` 把决定回写，工具才会继续。

四条判定为不批准的路径：

| 情形 | 位置 | reason |
|---|---|---|
| 会话已取消 | `:82-93` | `user_cancelled` |
| 无确认通道 | `:130-148` | `no_confirmation_manager`，同时记 `kernel_tool_confirmation_missing_total` 指标 |
| 用户显式拒绝 | `:176-184` | 直接返回 false |
| 确认异常或超时 | `:185-197` | `confirmation_timeout` |

### 5.3 不经过确认门的路径

以下路径按设计不逐次确认，实现或修改权限逻辑时必须考虑：

| 路径 | 机制 | 位置 |
|---|---|---|
| `auto` / `plan` 模式 | `confirmationPolicy` 返回 `undefined` | `kernel-session-policies.ts:45-46` |
| locked agent（`asset` 类型） | 自动批准全部工具 | `kernel-tool-confirmation.service.ts:103-127`、`locked-agent.policy.ts:25-30` |
| query lane 只读工具 | SDK 侧按 `yoloLanes` 跳过 | `yoloLanes: ['query']` |
| 已授权作用域 | once / task / session 三档，后两档在有效期内不再弹窗 | `websocket-confirmation-manager.ts:213-223` |
| 客户端可信工具自动应答 | 仍需回写服务端 | `hitl-auth.ts:370-401`、`connection.ts:946-957` |
| REST 消息通道 | 不带确认器，需确认的工具直接判定 `no_confirmation_manager` | `kernel-session-runtime.controller.ts:139-145` |

工具的读写分类主要在 `@a3s-lab/code` 4.2.1 内部，不在本仓库，无法在本仓库侧完整枚举。

### 5.4 批准记录

当前批准状态保存在进程内与浏览器 localStorage（上限 100 条，`hitl-auth.ts:99-104`、`407-422`）。**没有服务端持久化审计表。**

## 6. 知识库子系统

### 6.1 摄取管线

`apps/sidecar/src/modules/assets/application/knowledge-ingestion.service.ts`

```text
scanning     枚举 raw/sources 下的来源
   ↓
extracting   按 MIME 抽取纯文本（txt / pdf / docx / xlsx / 图片 OCR）
   ↓
chunking     切分为固定窗口的 chunk，写入定位元数据
   ↓
embedding    构建向量索引
   ↓
publishing   写 manifest，发布索引修订号
```

关键常量：

```ts
const MAX_SOURCE_BYTES     = 50 * 1024 * 1024;   // 单来源 50 MB 上限
const MAX_EXTRACTED_CHARS  = 10 * 1024 * 1024;   // 抽取文本 10 M 字符上限
const CHUNK_SIZE           = 1_200;
const CHUNK_OVERLAP        = 160;
```

### 6.2 增量复用

`reindex()` 对每个来源计算内容 SHA，与上一次 manifest 比对：

```ts
const sha = blob.contentSha || createHash('sha1').update(bytes).digest('hex');
const previousEntry = previousByPath.get(path);
if (previousEntry?.sha === sha && (await this.entryArtifactsExist(assetId, previousEntry))) {
    sources.push(previousEntry);
    reusedSourceCount += 1;
    continue;
}
```

两个条件必须同时满足才复用：内容指纹一致，且 `extracted/` 与 `chunks/` 派生产物确实可读（`entryArtifactsExist`，`:624-631`）。后者防止「指纹命中但产物已丢失」导致的假复用。

复用数量通过 `reusedSourceCount` 回报给调用方。

`options.sourcePaths` 支持定向重建指定来源（`:152-156`），未指定时处理全部来源。

`writeTextIfChanged`（`:634-637`）在内容字节相同时跳过写入，避免无谓的 git 提交。

**复用范围限于抽取与切分两个阶段。** 向量索引在 `:252` 由 `buildVectorIndex(asset, sources, now, signal)` 对全部来源无条件重建，没有 per-chunk 嵌入缓存。

### 6.3 来源状态机

| 状态 | 含义 |
|---|---|
| `indexed` | 抽取成功，已切分并计入索引 |
| `waiting_for_ocr` | 未抽取到文本且 OCR 后端未启用 |
| `unsupported` | MIME 类型不支持 |
| `error` | 超过大小上限，或抽取过程抛异常 |

失败条目仍写入 manifest（`failedEntry`），带 `retryable` 标记，前端据此显示「重新抽取」或「配置后重试」。

### 6.4 Chunk 定位元数据

切分阶段为每个 chunk 写入完整定位信息（`:553-566`）：

```ts
chunks.push({
    id: `${contentSha}:${chunks.length}`,
    index: chunks.length,
    sourcePath,
    mime,
    contentSha,
    charStart: start,
    charEnd: end,
    lineStart: this.positionFromBreaks(lineBreaks, start),
    lineEnd: this.positionFromBreaks(lineBreaks, end),
    pageStart: this.positionFromBreaks(pageBreaks, start),
    pageEnd: this.positionFromBreaks(pageBreaks, end),
    text: chunkText,
});
```

`lineBreaks` 与 `pageBreaks` 是抽取阶段产出的偏移表。页码依赖抽取器输出分页符（`\f`）——PDF 有页概念，纯文本没有，此时 `pageStart/pageEnd` 为空。

### 6.5 检索

`apps/sidecar/src/modules/assets/application/knowledge-query.service.ts`

融合点在 `searchAssets()`（`:269-379`），四个阶段：

**1. 加权关键词匹配**（`:580-607`）

| 字段 | 权重 |
|---|---|
| 标题 | ×8 |
| 描述 | ×5 |
| 标签 | ×4 |
| 路径 | ×2 |
| 正文 | ×1 |

额外有短语连续命中加成。

**2. 向量相似度** —— 余弦相似度，覆盖 OKF 概念页与来源 chunk 两类对象。

**3. 加权融合**

```text
score = keyword × kw + semantic × vw     // 默认 kw:vw = 1:6
```

**4. MMR 多样性重排**（`:528-556`）—— 抑制同源、同段的重复命中。

**纯语义命中准入闸**（`:458-470`）：

| 嵌入类型 | 门槛 |
|---|---|
| 本地哈希向量 | 相似度 ≥ 0.12 **且** 与查询有词元重叠 |
| 外部嵌入 | 相似度 ≥ 0.30 |
| 标识符类查询 | 拒绝纯语义命中，必须有规范化词元锚点 |

这道闸是为修复「随机标识符被最近邻误命中」问题加入的。

**未实现**：BM25、RRF 融合、独立重排模型。

### 6.6 向量与嵌入

默认使用离线特征哈希向量：

```ts
// assets/domain/knowledge/local-embedding.ts:3-4
provider: 'local-hash-v1'
dimensions: 192
```

内含手工维护的中英同义归一表。这不是学习式嵌入。

远端嵌入由 `knowledge-embedding.service.ts:45-155` 支持，走 OpenAI 兼容的 `/embeddings` 接口，批大小 64，重试 3 次，并校验返回维度一致。切换方式是在资产的 `metadata.knowledge.embedding` 中配置 provider。

### 6.7 图谱与健康度

`knowledge-graph.service.ts:187-245` 计算：

- **brokenLinks** —— wiki 链接指向不存在的页面
- **orphanPages** —— 没有任何入链的页面

图关系与反向链接是独立端点（`wiki/graph`、`wiki/backlinks`、`wiki/similar`），**不参与主检索的分数融合**。

### 6.8 自评接口

`POST /assets/:id/wiki/evaluate`（`knowledge-query.service.ts:80-113`）接受一组「问题 → 期望命中路径」，返回 recall@K、MRR 与空结果率。用于在自有问题集上评估检索配置，不是内置基准。

## 10. 前端架构

### 10.1 路由

`apps/web/src/desktop/router.tsx` 使用 hash 路由：

### 10.2 文件编辑器

`components/workspace/file-tree-editor/FileTreeEditor.tsx` 是一个基于 Dockview 的多面板编辑器，被知识库页、技能页和会话工作区对话框共用。

特性：

- VS Code 风格活动栏（资源管理器、搜索、源代码管理 + 可注入的自定义面板）
- 多标签，脏标记
- 布局与已打开标签按工作区根目录持久化（`:9235-9254`、`:1113-1171`）
- 命令面板与快速打开

知识库页强制 Markdown 源码模式（`enableRichMarkdown={false}`），以保证 YAML frontmatter 在保存后不被富文本编辑器改写。

### 10.3 会话连接

`apps/web/src/kernel/session/connection.ts` 管理 WebSocket 会话通道，处理流式事件、工具确认往返、断线重连。

工具确认对话框为 `components/custom/tool-confirmation-dialog.tsx`，提供三档授权作用域（`once` / `task` / `session`），关闭对话框等同拒绝。

### 10.4 前后端类型差异

`apps/web/src/lib/api/assets.ts:1290-1301` 定义的 `WikiSearchHit` 只含 `title`、`path`、`snippet`、`score`。

后端 `KnowledgeSearchHit`（`knowledge-query.service.ts:16-32`）返回的 `citations`、`kind`、`assetId`、`chunkIndex` 字段在这个前端类型中缺失。**知识库页的搜索结果因此不显示页码或行号定位。** 定位数据存在于 API 响应中，只是这一处 UI 未渲染。

`?source=` 查询参数可以在页面加载时自动打开被引用的文件（`KnowledgePage.tsx:90-101`）。
